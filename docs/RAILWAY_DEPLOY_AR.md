# تشغيل نظام المحل على Railway

هذه نسخة مستضافة اختيارية؛ التشغيل المحلي على Windows يظل متاحًا.
الاستضافة **تحتاج إنترنت للبيع**. لا توجد مزامنة بين قاعدة المحل والقاعدة المستضافة.
لا تستخدم النسختين لإدخال عمليات حقيقية بالتوازي.

## أول نشر — بقاعدة فارغة للاختبار

1. استخدم آخر commit على `main`. بناء Docker يشغّل اختبارات الاستضافة تلقائيًا
   على Linux، بما فيها PDF، ويرفض البناء عند فشلها.
2. في Railway: أنشئ مشروعًا وخدمة من GitHub واختر
   `Usama1917/Local-First-Pos`، الفرع `main`، وجذر المشروع `/`.
   اترك البناء لـ`Dockerfile` وإعدادات `railway.json`، دون Build/Start command مخصص.
3. أضف **Volume** لنفس الخدمة، واجعل Mount Path هو **`/data`**.
   قاعدة البيانات ليست PostgreSQL؛ لا تضف خدمة قاعدة بيانات ثانية.
4. تسجيل الدخول **مغلق افتراضيًا**، لذلك لا تحتاج بيانات دخول لفتح النظام مباشرة.
   لو أردت تفعيله لاحقًا، أضف المتغير التالي مع بيانات المدير:

   ```text
   POS_AUTH_ENABLED=1
   POS_ADMIN_USERNAME=<اسم مدير تختاره، مطلوب فقط عند تفعيل تسجيل الدخول>
   POS_ADMIN_PASSWORD=<كلمة مرور فريدة من 12 حرفًا على الأقل، مطلوب فقط عند تفعيل تسجيل الدخول>
   ```

   اكتب القيم الحقيقية في Railway فقط، لا في GitHub أو المحادثة.
   يُفضّل كلمة عشوائية طويلة محفوظة في مدير كلمات مرور.
5. Dockerfile يضبط تلقائيًا:

   ```text
   NODE_ENV=production
   POS_HOSTED=1
   POS_DATA_DIR=/data
   POS_CONFIG_DIR=/data/config
   POS_ARCHIVE_DIR=/data/archive
   TZ=Africa/Cairo
   ```

   Railway يضبط `PORT` و`RAILWAY_VOLUME_MOUNT_PATH`. لا تزوّر متغير الـVolume يدويًا.
6. نفّذ Deploy. فشل التشغيل قبل إضافة الـVolume **مقصود للحماية**. وإذا فعّلت
   تسجيل الدخول، فشل التشغيل قبل إضافة بيانات المدير مقصود أيضًا؛ أضف الناقص ثم
   أعد النشر. لا تستخدم Pre-deploy command لتهيئة SQLite:
   الـVolume متاح أثناء التشغيل، وليس أثناء البناء.
7. اترك **نسخة واحدة فقط** من الخدمة. لا Replicas متعددة ولا تشغيل خدمتين على الملف نفسه.
8. بعد نجاح `/api/healthz`، من Networking اختر Generate Domain ثم افتح رابط HTTPS.
   الواجهة و`/api` على نفس الرابط، وتفتح مباشرة في الوضع الافتراضي. إذا فعّلت
   `POS_AUTH_ENABLED=1` ستظهر شاشة الدخول بالبيانات التي اخترتها.
9. جرّب ببيانات غير حقيقية: منتج، حساب موظف وصلاحياته، بيع، مرتجع، طباعة،
   أرشفة PDF، تنزيل نسخة احتياطية، ثم Restart وتأكد أن البيانات ما زالت موجودة.
10. راقب RAM/CPU والفاتورة، خصوصًا أثناء إنشاء PDF. ضع تنبيه تكلفة.
    **Hard limit قد يوقف نظام البيع** عند بلوغه؛ لا تختَر حدًا ضيقًا بلا متابعة.

بعد إنشاء المدير يمكنك حذف `POS_ADMIN_PASSWORD` من Variables وإعادة النشر:
المتغير يُستخدم فقط إذا كان جدول المستخدمين فارغًا. تغييره **لا يعيد تعيين**
كلمة مرور مستخدم قائم؛ تغييرها من شاشة المستخدمين.

## ما الذي تغيّر في وضع الاستضافة؟

- لا بيانات تجريبية ولا حساب مدير بكلمة مرور افتراضية.
- كلمات المرور محفوظة كـscrypt hashes ولا يمكن عرضها للمدير؛ يمكنه تعيين كلمات جديدة.
- جلسات الدخول تنتهي بعد 12 ساعة. تسجيل الخروج وتغيير كلمة المرور يلغي الجلسة.
- تحديد محاولات الدخول، وعدم كشف أخطاء السيرفر التفصيلية في الردود العامة.
- صلاحيات سيرفر للعمليات، مع السماح ببيانات البحث المشتركة اللازمة للشاشات
  (مثل المنتجات والعملاء للكاشير). **هذه ليست صلاحيات على كل حقل أو سجل**:
  بيانات البحث الحالية قد تتضمن تكلفة المنتج أو رصيد العميل.
- صلاحية `/pos` تسمح بعمليات المبيعات؛ تحويل تسعيرة لفاتورة يحتاج أيضًا
  `/pos` أو `/sales`. تعديل فاتورة من الكاشير يحتاج `/pos`.
- مسودات كل نوع مشتركة بين أصحاب صلاحية نفس الشاشة، كما في النظام المحلي.
- بيانات المراجعة `createdBy` تأتي من الجلسة، لا من اسم يرسله المتصفح.
- مسارات البيانات والأرشفة ثابتة على الـVolume؛ تصفح مجلدات جهاز المحل غير متاح.
- صورة Docker تشمل Chromium وخطوط عربية. PDF يُنشأ واحدًا كل مرة لتقليل الذاكرة.
- طباعة المتصفح تظل على جهاز المستخدم وطابعته. ملفات الأرشيف التلقائي على السيرفر؛
  ليست متزامنة مع مجلد Windows. يمكن للمسؤول استخراجها عبر اتصال Railway الآمن.

## الملفات الدائمة والنسخ الاحتياطي

| المسار | المحتوى |
|---|---|
| `/data/store.db` مع `-wal` و`-shm` أثناء التشغيل | قاعدة البيانات |
| `/data/archive/` | أرشيف PDF |
| `/data/config/` | إعدادات التشغيل وبيانات النسخ المشفّر إذا تم إعداده |
| `/data/backups/` | النسخ اليدوية ولقطات SQLite اليومية |
| `/data/logs/` | سجل النسخ إلى GitHub |

- ينشئ السيرفر لقطة SQLite متسقة يوميًا (بعد دقيقة من التشغيل ثم يفحص كل ساعة)،
  ويحتفظ بآخر 7 لقطات `auto-YYYY-MM-DD.db`. لا يحذف النسخ اليدوية.
- **لقطة داخل نفس الـVolume لا تحمي من فقد الـVolume نفسه.**
  فعّل Railway Volume Backups بعد مراجعة تكلفتها، واختبر الاستعادة.
- النسخ المشفّر إلى GitHub متاح من شاشة الإعدادات إذا جهزت ريبو **خاصًا**
  وتوكنًا محدود الصلاحيات وكلمة تشفير منفصلة. بعد الإعداد يفحصه السيرفر كل ساعة
  ويرفع نسخة عند مرور 24 ساعة من آخر رفع؛ لا يرفع تلقائيًا إلى أي حساب غير مُعد.
- احفظ كلمة التشفير خارج السيرفر في مكان آمن؛ ضياعها يمنع فتح النسخ.
- زر تنزيل النسخة اليدوية ينتج ZIP يحتوي قاعدة البيانات فقط، **لا PDF ولا إعدادات
  النسخ المشفّر**. عامله كملف حساس ولا ترفعه في المستودع.
- راقب مساحة الـVolume: اللقطات والـPDF والنسخ اليدوية تستهلك مساحة.
  الحد المعتاد لـHobby ليس مساحة غير محدودة؛ راجع لوحة Railway قبل نقل بيانات كبيرة.
- تحديث خدمة مرتبطة بـVolume قد يسبب انقطاعًا قصيرًا؛ اختَر وقتًا خارج البيع.

## نقل بيانات المحل الحقيقي — خطوة منفصلة

لا ترفع `data/` أو ZIP أو ملفات إعدادات المحل إلى GitHub أو داخل صورة Docker.

1. اختبر النسخة المستضافة أولًا، وحدد موعد توقف البيع.
2. على النسخة المحلية، عيّن كلمات مرور قوية (12 حرفًا على الأقل) لكل الحسابات النشطة.
   يتوقف السيرفر المستضاف إذا وجد حسابًا نشطًا بكلمة نصية قصيرة.
3. من الإعدادات أنشئ نسخة ZIP حديثة متسقة، ونزّلها واحفظ نسخة أصلية خارج السيرفر.
   **لا تنسخ `store.db` وحده من قاعدة تعمل في WAL.**
4. أوقف الإدخال على المحلي، وأوقف السيرفر المستضاف قبل استبدال قاعدة الاختبار.
   انقل لقطة `store.db` عبر قناة إدارية آمنة إلى الـVolume، بعد حفظ نسخة قابلة
   للاسترجاع من الملفات الموجودة هناك. لا تستبدل قاعدة حية ولا تخلط WAL قديمًا معها.
   نقل الملف/استعادته يحتاج إجراء إداري منفصل؛ زر الاستعادة داخل التطبيق غير مفعّل.
5. لا تنقل `pos-config.json` بمسارات Windows. الأرشيف القديم يُنقل منفصلًا إن احتجته.
6. أول تشغيل يحوّل كلمات المرور النصية القديمة إلى hashes ويلغي الجلسات المحلية.
   بيانات المدير من Variables لا تستبدل الحسابات الموجودة في النسخة المنقولة.
7. قارن إجماليات المخزون والمديونيات والفواتير قبل وبعد النقل، ثم افتح البيع
   على المستضاف فقط. احتفظ بالأصل المحلي كنسخة رجوع لا يُدخل عليها عمليات جديدة.

هذا التجهيز لا يُغني عن اختبار قبول فعلي بحسابات وصلاحيات المحل، ولا يُعد
تدقيقًا أمنيًا شاملًا لكل منطق الحسابات والفواتير الموجود.

## التحقق للمطوّر

```sh
pnpm install --frozen-lockfile
pnpm run typecheck
pnpm run build:shop
pnpm run test:hosting

docker build -t local-first-pos:test .
docker run --rm -e REQUIRE_PDF=1 \
  -v "$PWD/tests:/app/tests:ro" --entrypoint node \
  local-first-pos:test --test tests/hosting.test.mjs
```

الاختبارات تنشئ قواعد مؤقتة ولا تلمس `data/store.db` أو إعدادات المحل.
اختبار Docker يعمل تلقائيًا داخل `docker build`، بما في ذلك بناء Railway.
يستغرق الاختبار حوالي دقيقة إضافية للتحقق من النسخ التلقائي.

المراجع: [Dockerfile](https://docs.railway.com/builds/dockerfiles)،
[إعدادات النشر](https://docs.railway.com/config-as-code/reference)،
[Volumes](https://docs.railway.com/volumes/reference)،
[Healthchecks](https://docs.railway.com/deployments/healthchecks).
